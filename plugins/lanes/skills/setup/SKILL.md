# Lanes setup

Arguments: `$ARGUMENTS`

**SKILL_DIR** = `${CLAUDE_SKILL_DIR}`. If the backticks above show the literal text `${CLAUDE_SKILL_DIR}`, this file was
opened without the skill loader (the path in `SETUP.md` at the root of the claude-role-lanes repository). Then
SKILL_DIR is the directory that contains this file.

You install the role lanes into a git repository, the **TARGET**. The lanes are four session roles (Default,
Discovery, Development, Release), three hard rules, and a branch flow `work -> queue -> main -> prod`. Read
`SKILL_DIR/reference/config.md`, `SKILL_DIR/reference/interview.md` and `SKILL_DIR/reference/rendering.md` before
Step 1.

## Rules for this procedure

1. **Templates are copied verbatim except their tags** (`reference/rendering.md`). Never paraphrase template text.
2. **Write only** `.claude/lanes.yml`, the Step 6 targets, and side-by-side files under `.claude/lanes-new/`. Write
   nothing else in the TARGET, except a `.gitignore` change the user approves in Step 4. Scratch work goes in memory or in your scratchpad, never in the TARGET.
3. **Outward-facing actions need an explicit yes in chat:** creating or editing GitHub labels, committing, pushing.
   Setup never commits or pushes on its own.
4. **No secrets in `.claude/lanes.yml`.** It is committed. If an answer contains a password, token, connection string
   or key, store a pointer instead ("credentials: see `appsettings.Secrets.json`, gitignored").
5. **Ask at most 4 questions per `AskUserQuestion` call.** The detected or default value is the first option. If
   `AskUserQuestion` is not available, ask in chat.
6. **Never overwrite a file the user owns.** A generated file carries the line `generated by claude-role-lanes`. A
   file without it is owned. `CLAUDE.md` is the exception: setup only ever replaces the text between its
   `lanes:begin` / `lanes:end` markers, or inserts the block (Step 4).

## Mode

| Condition | Mode | Steps |
|---|---|---|
| Arguments contain `check` | CHECK | 0.1, 0.4, 4 (states only), 5, then compare and report. Write nothing; ask nothing but 0.1. |
| `.claude/lanes.yml` exists | UPGRADE | 0, 1, then the UPGRADE interview (below), then 3-9. |
| Otherwise | NEW | 0-9. |

**UPGRADE interview.** Ask only for keys that `config.md` lists, that apply under the current config, and that
the file lacks. A key inside a module whose `enabled` is `false` does not apply. Neither does a key whose condition
is not met (for example `branches.release` under topology `main`). Then show one table of every key where Step 1
**detected a value** that differs from the configured one (a probe that found nothing is not drift), plus any
CLAUDE.md candidate not yet in `conventions` or `hard_rules`. Ask once: "Update any of these?" Default: keep the
configured values.

## Step 0 - Preflight

1. `git rev-parse --show-toplevel` gives the candidate TARGET. If it fails, stop: setup needs a git repository.
   **Confirm the TARGET with the user**: "Install the lanes into `<path>`?" A session's working directory is not always
   the project the user means.
2. `gh auth status`, then `gh repo view --json nameWithOwner`. **GitHub is available** only if both succeed. If not,
   continue, and tell the user: detection is partial, Step 8 (labels) is skipped, and the rendered roles call `gh`, so
   they need it later.
3. NEW and UPGRADE only: `git status --porcelain`. If the tree is not clean, say so and recommend running setup on a
   new branch (`git switch -c lanes/setup`). Ask before continuing.
4. Read `version` from `SKILL_DIR/../../.claude-plugin/plugin.json`. That is the plugin version.

## Step 1 - Detect

Run every probe in `reference/interview.md` > "Detection". They are read-only. Build a draft config in memory, with
the evidence for each detected value. In UPGRADE mode the draft is used only for the drift table.

## Step 2 - Interview

NEW mode: ask the pace question, then follow the rounds in `reference/interview.md`. Show each detected value with its
evidence. Never present a default as if it were detected.

## Step 3 - Write `.claude/lanes.yml`

- **NEW mode.** Assemble the config with the keys in the order of `config.md`. Start the file with these two lines:
  ```
  # claude-role-lanes configuration. Edit, then run /lanes:setup to re-render.
  # Reference: https://github.com/Revelation-Hosting/claude-role-lanes/blob/main/plugins/lanes/skills/setup/reference/config.md
  ```
- **UPGRADE mode.** Edit the existing file in place. Add each new key at the end of its section. Change only the keys
  the user changed. Keep every comment, the key order and the YAML style (flow lists stay flow lists). Set
  `lanes_version` to the plugin version.
- In both modes: check the result against `config.md`. Every required key has a value. A required list may be `[]`.
  Each enum holds an allowed value. Each color is 6 hex digits. Every string value setup writes is double-quoted
  (config.md explains why).
- If the result is byte-identical to the file on disk, say "`.claude/lanes.yml` unchanged" and do not write it.
  Otherwise show the whole file (NEW) or the diff (UPGRADE) in chat and ask: "Write `.claude/lanes.yml`?" Write it on
  a yes.

## Step 4 - Plan the writes

For each Step 6 target (the paths are known now), record its state: **absent**, **generated** (carries the marker), or
**owned** (exists without the marker). For `CLAUDE.md`, record **markers**, **no markers** or **no file**. Show one
table: target path, state, action.

| State | Action |
|---|---|
| absent | create |
| generated | re-render (show a diff summary in Step 6) |
| owned | ask, with options in this order: (a) write the new version to `.claude/lanes-new/<target path>.new` for a manual merge (Recommended), (b) overwrite, (c) skip |

**Ignored targets.** Run `git check-ignore -v` on every target and on `.claude/lanes.yml`. A target that an ignore
rule matches would never be committed, so no teammate and no fresh clone would get it. Show the matching rule and
propose the narrowest change. Example: replace `.claude/` with `.claude/*`, `!.claude/agents/`,
`!.claude/agent-memory/` and `!.claude/lanes.yml`, so local state (`settings.local.json`, `worktrees/`) stays ignored.
Edit `.gitignore` only on a yes.

Tell the user what (a) means for an agent file: the owned `.claude/agents/<role>.md` stays the file Claude Code loads
until they merge.

**`CLAUDE.md`.** Read its full text and keep it in memory for V4 before you change it.

- **markers:** replace the text from `<!-- lanes:begin` through `<!-- lanes:end -->`. Leave everything else as it is.
- **no markers, file exists:** ask where the block goes.
  - **Top (Recommended)**, so the first-turn rule is read early. Skip any YAML front matter and the first `# ` heading
    line. If the next non-blank lines are a paragraph (plain text, not a heading, list, table or fence), skip them too.
    The insertion point is the first blank line after what was skipped. Keep that blank line. Insert the block lines
    after it, then **one** new blank line. With no blank line left (end of file), add one blank line, then the block.
  - **Bottom:** if the file does not end with a blank line, add one. Then append the block.
  - Setup adds exactly one blank line outside the markers. V4 removes the block and that one line.
- **no file:** create it with `# <project.name>`, one blank line, then the block.

## Step 5 - Render

Render every template in the Step 6 table in memory, by `reference/rendering.md`. Run the self-check for each file.

**CHECK mode stops here.** First report the plugin version (0.4) beside `lanes_version`. If the plugin is newer,
recommend a normal run to upgrade. Then, for each target, compare the render with what is on disk (for `CLAUDE.md`,
the block from the `lanes:begin` line through the `lanes:end` line, both included). Report, per file: `in sync`, `differs` (with the changed lines), `absent`, or `owned` (not
compared). For an owned file with a side-by-side file in `.claude/lanes-new/`, also report whether the side-by-side
file is `in sync` with the render. A generated file that differs was edited by
hand. Recommend moving the edit into `.claude/lanes.yml` (`roles.<role>.extra`, `conventions`, `hard_rules`), into
`CLAUDE.md` outside the markers, or deleting the marker line to take ownership. Write nothing.

## Step 6 - Write

| Template (`SKILL_DIR/templates/`) | Target |
|---|---|
| `CLAUDE.lanes.md` | `CLAUDE.md`, by the Step 4 rule |
| `agents/discovery.md` | `.claude/agents/discovery.md` |
| `agents/development.md` | `.claude/agents/development.md` |
| `agents/release.md` | `.claude/agents/release.md` |
| `docs/RELEASE-PROCESS.md` | the value of `paths.process_doc` |
| `docs/runbooks/TEMPLATE-release-runbook.md` | `<paths.runbook_dir>/TEMPLATE-release-runbook.md` |
| `github/ISSUE_TEMPLATE/bug-report.md` | `.github/ISSUE_TEMPLATE/bug-report.md` |

Write each file by its Step 4 action. A side-by-side file goes to `.claude/lanes-new/<target path>.new` (for example
`.claude/lanes-new/.claude/agents/discovery.md.new`). The `.new` extension keeps Claude Code from loading it as an
agent. Show a diff summary for each re-rendered file: lines added and removed, and the headings that changed. Create parent directories as needed. Write UTF-8
without a byte-order mark, with the line endings the repository already uses (an existing text file decides; default
LF).

## Step 7 - Verify

Run every check on every file written in Step 6, including side-by-side files. Report a table: check, result
(`PASS` / `FAIL` / `WARN` / `N/A`), evidence.

| # | Check | Pass when |
|---|---|---|
| V1 | Leftover tags | A search for `{{` finds 0 matches in each written file. In `CLAUDE.md`, search only between the markers. |
| V2 | Agent frontmatter | Each rendered agent file opens with `---` on line 1, has `name:` equal to the role (`discovery`, `development`, `release`), has `description:`, and closes its frontmatter with `---`. Every line inside the `initialPrompt: \|` block starts with 2 spaces. |
| V3 | CLAUDE.md markers | Exactly 1 `<!-- lanes:begin` and 1 `<!-- lanes:end -->`, in that order. |
| V4 | CLAUDE.md outside the block | Remove the block and the separator blank lines Step 4 added. The rest is byte-identical to the text kept in Step 4. |
| V5 | Named paths exist | Each of these exists in the TARGET: `ci.workflow`; each `release.prod_lanes[].workflow` under `.github/workflows/`; `database.migrations_dir`; `database.base_schema_dir`; each `roles.discovery.may_edit[].path`; at least 1 tracked file (`git ls-files`) per `release.main_push_prod_paths` pattern. A missing one is `WARN` (it may be planned). A key in a disabled module is `N/A`. V7 does not report these again. |
| V6 | One topology | The rendered Release role contains exactly one lanes diagram: one fenced block whose first line starts with the work-branch pattern. |
| V7 | Read-through | Read each written file once, top to bottom. List each sentence that is false for this project. Classify each one (below). |
| V8 | Nothing ignored | `git check-ignore` prints nothing for each Step 6 target and for `.claude/lanes.yml`. An ignored file is `FAIL` unless the user chose in Step 4 to keep it local; then `ACCEPTED`. |

**V7 classes:**

- **Config value wrong** (the sentence comes from a value, and the repository shows a different fact): `FAIL`.
  Collect every such row. Show them in one table (key, rendered sentence, evidence) and ask the user, once, which to
  correct; offer "Correct all (Recommended)" when the evidence is a file in the repository. For each corrected key,
  show the `.claude/lanes.yml` diff and write it on a yes. Then repeat Steps 4-7 for every file: Step 4 re-reads the
  states, so `CLAUDE.md` now has markers and its block is replaced, never inserted twice. A value the user keeps is
  `ACCEPTED`: add `{key, reason}` to `verification.accepted` in `.claude/lanes.yml` (show the diff, write on a yes).
  V7 skips a key listed there while its value is unchanged.
- **Template text false for this project** (no config value controls it): `WARN`. Quote it. Offer the user three
  remedies: text in `roles.<role>.extra`, a note in `CLAUDE.md` outside the markers, or deleting the marker line to
  take ownership of that file. Suggest reporting the template defect at
  `https://github.com/Revelation-Hosting/claude-role-lanes/issues`. List the WARNs and these remedies in the Step 9
  hand-off; take no action on them. A `WARN` does not block Step 8.
- **Cannot tell** (the repository has no evidence either way, for example a tool that runs on another machine, or
  a precondition not met yet, such as no GitHub remote): `N/A`, with one line saying what would settle it.

Resolve every `FAIL` (corrected, or `ACCEPTED`) before Step 8 and Step 9.

## Step 8 - GitHub labels

Skip this step if GitHub is not available (Step 0.2). Otherwise:

1. Build the label list: `tracker.backlog_label`; `tracker.scope_question_label` if set; one label per
   `tracker.risk_types` item (name = `name`, color = `color`, description = the first sentence of `definition`, cut
   to 100 characters); `S1`..`S4` if `tracker.severity_labels`.
2. Compare it with `gh label list --limit 200 --json name,color,description`. Show a table: label, `create` /
   `update` (with the change) / `unchanged`.
3. Ask: "Create or update these labels on <owner/repo>?" Only on a clear yes, run
   `gh label create "<name>" --color <hex> --description "<text>" --force` for each `create` or `update` row.
4. Run `gh label list` again and confirm each label exists with its color.

## Step 9 - Hand-off

Report, in this order:

1. Files written, with their action (created / re-rendered / written beside / skipped / unchanged).
2. The Step 7 table.
3. Labels created or updated, or "skipped" with the reason.
4. **Not verified:** setup did not run the roles. Say so plainly.
5. Side-by-side files waiting for a manual merge, if any. Delete `.claude/lanes-new/` after the merge.
6. How to use the roles:
   - Terminal: `claude --agent discovery` (or `development`, `release`). This replaces the system prompt.
   - Claude Desktop: start a new session in this repository. The CLAUDE.md block makes the session ask for its role.
   - In any session: `@discovery` runs the role as a subagent for one task.
7. Suggested commit, for the user to approve. Stage only the generated files and `.claude/lanes.yml`, never
   `.claude/lanes-new/`:
   `git add CLAUDE.md .claude/lanes.yml <each written .claude/agents file> <process doc> <runbook template> .github/ISSUE_TEMPLATE/bug-report.md`
   then `git commit -m "Add role lanes (claude-role-lanes <lanes_version>)"`. Run it only on a clear yes.
8. Upgrade path: update the plugin, then run `/lanes:setup` again. It asks only for new keys.
